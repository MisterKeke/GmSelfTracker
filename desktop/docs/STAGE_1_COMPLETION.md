# Stage 1 completion report

**Stage 1 is complete. Stage 2 was not started.** This report covers the master specification's data foundations, accounts, schema editing, and safe field migration work.

## Web (Go/JavaScript)

The Web implementation remains the behavior and data-format reference; no Web code was changed for this desktop-focused stage. The reference suites pass: `go test ./...` and `node --test web/js/tests/*.test.mjs` (24 frontend tests).

## Desktop (C++/Qt)

- Added bcrypt-backed local registration, login, account switching/locking, password change, and account ownership isolation. The last username may be remembered in QSettings; passwords are not. Existing local installations keep their original profile ID and data, with an explicit action to add credentials to that profile.
- Added the native “Import Existing GmSelfTracker Data” workflow. It accepts version-11 Web databases, reads a consistent read-only SQLite snapshot including WAL data, validates schema/integrity/foreign keys, stages and verifies uploads, preserves source IDs and records, and rolls back target rows and installed assets on handled failure.
- Added object type editing, archive/restore, fallback image and primary-display configuration. Added field editing for stable-ID metadata, defaults, options, sort order, references and formulas, plus archive/restore. Select option removals require value/default replacements.
- Added a field type migration wizard and transactional service. It previews conversions and dependencies across active and archived values, defaults, formulas and relationships; blocks incompatible dependencies; requires explicit choices for lossy policies; checks stale preview tokens; and records migrations and Object History.
- Raw numeric JSON is preserved during migration when the target representation supports it. A regression test migrates `9007199254740993` and checks that both the stored value and field default keep those exact digits.
- Native authentication tests verify a Web-compatible bcrypt hash. A separate interoperability check verified that Go's bcrypt implementation accepts a hash generated by the desktop implementation.

## Shared compatibility

The native importer accepts the Web version's contiguous schema migration history through version 11 and copies all game-data tables plus `asset_references`. It does not import browser sessions or Web migration rows; desktop continues to migrate its own database. Account IDs and bcrypt hashes are preserved, so imported users sign in again through the native account dialog. ID and username conflicts stop import without replacing existing desktop records. The Web and desktop live databases remain separate.

No schema migration was added: Stage 1 uses the existing version-11 schema and its recorded migration positions. Fresh disposable databases are created by the existing runner for the native workflow tests; import fixtures use the same embedded migration set.

Disposable database tests cover an active-WAL import fixture with multiple games, archived records, references, history, templates, presets, dashboards, gallery metadata, primary display configuration and shared assets; missing-asset rollback; account/password flows and legacy ownership; type/field edits and restore; conversion cases including archived values and formula freezing; dependency rejection; stale previews; and transaction rollback. This verifies the v11 data contract with a source-compatible fixture, not an actual user's Web database.

## Remaining limitations

- No actual user database or uploads directory was imported; source compatibility was checked with a disposable source-migration fixture.
- The importer accepts Web schema version 11 only. Browser sessions are intentionally excluded, so imported accounts authenticate again in the desktop app.
- Failure and retry behavior is covered, but forced process termination at every file/commit boundary and every filesystem permission failure were not separately simulated.
- Full desktop parity beyond Stage 1 is incomplete: Stage 2 browsing/view behavior and later templates, presets, dashboards, recursive progress, gallery, comparison and relationship graph work remain. No Stage 2 implementation was made here.
- Portable packaging and clean-machine deployment checks were not run for this stage.
