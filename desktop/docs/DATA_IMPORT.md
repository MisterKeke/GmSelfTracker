# Data import status

The import wizard requested for the desktop port is not implemented yet. The current app creates its own database at `QStandardPaths::AppLocalDataLocation` and runs the same inspected SQLite migrations 001–011. Native image uploads now live in an `uploads/` directory beside that desktop database and are owned by the local profile. This image library does not select, copy, open, or modify a GameTracker website database or its uploads directory. No source snapshot, import activation, conflict handling, or retry workflow has been verified.

## Planned import contract

The implementation must select a source SQLite file and uploads folder, take a SQLite-supported consistent snapshot including active WAL state, leave the source untouched, validate schema version and integrity, preserve user hashes and all feature rows, copy asset files safely, and verify foreign keys and asset references before completion. It must report skipped rows and rollback the target transaction on failure. Existing source files must never be deleted or overwritten. The activation policy is still undecided: before import code writes data, define staging, how an imported account is selected alongside an existing local profile, how repeat imports and ID collisions are reported, and how the prior desktop profile remains available if publication fails. Treat unsupported or corrupt input as unrecoverable for that attempt, retain the source unchanged, discard only the staged destination, and allow a safe retry after the user corrects or selects valid source files.

The source migration SQL has been copied into Qt resources so schema application can be developed independently of the Go server. The native migration runner applies one migration at a time in a transaction and recognizes quoted text, comments, and trigger bodies rather than splitting naively at every semicolon. A dedicated importer, SQLite backup API, asset copy service, and compatibility acceptance fixtures are still outstanding. The current separate web and desktop live-data stores remain independent and must not be opened for simultaneous writes.
